# Swedish company lookup: review notes

These notes accompany the live local-model benchmark. Original results and traces are retained unchanged under `data/company-lookup-local-20260927/`. They are observations, not corrected benchmark outcomes.

## Model identity

The saved `local Qwen` profile (revision 4, ID `657ff56f-2a12-4e84-8cdc-78fbbddb7093`) requests `RedHatAI/Qwen3.6-35B-A3B-NVFP4`. The endpoint reports `nvidia/Qwen3.8-27B-NVFP4` in its responses. The results therefore describe the endpoint actually served during this run; they must not be attributed to the configured Qwen3.6 model. No Jev model was submitted. Classification, identity extraction and candidate assessment use this same local endpoint.

## Confirmed findings

- **Addtech's original VAT conflict:** a Swedish VAT number such as `SE-556302972601` and organisation number `556302-9726` identify the same company. The deployed fix normalizes the explicit `SE…01` VAT form before searching and validating. Bare 12-digit IDs remain intact. Replaying the original saved facts and assessment accepts `5563029726`; this is an offline regression replay, not a successful fresh local-model crawl. The fresh local-model attempt failed at the identity call's 180-second deadline.
- **Stendörren:** the model proposed the correct company `5568254741` at confidence 0.99 with `basis=name_and_address`. The validated facts already contain the exact legal name, but the model did not provide a separate supported street-address fact. `accept_match` only considers the unique-name route when the model explicitly selects that basis. Replaying identical candidates/facts with only `basis=unique_legal_name` accepts the correct company. The raw model also changed the quoted organisation number `556825-4741` into unsupported `556825474101`; rejecting that fact was correct.
- **Instalco:** the correct candidate and explicit legal names were retrieved, but the address-basis gate caused another rejection. The page's `Sveavägen 56 C` / `111 34` and registry's `Sveavägen 56C` / `11134` also illustrate formatting differences. A reported postal-code fact can contain a city or other components; field schema and conservative normalization need improvement. Do not simply trust the model's confidence or loosen all evidence checks.
- **Norion:** the selected ESEF reference domain `norion.se` failed with `ERR_NAME_NOT_RESOLVED`. This is a source-domain/fetch failure, not evidence of an incorrect model decision.
- **Studsvik:** `studsvik.se` failed with `ERR_CERT_COMMON_NAME_INVALID`. TLS validation was preserved. This is a fetch failure, not a no-match decision.
- **Fabege:** the verified fact is `Fabege AB`, and the returned candidates contain exactly one company with that legal name (`5560491523`). The model nevertheless claimed the name was not unique because other, differently named candidates were returned. It selected the expected ID with confidence **1.0**, but marked its basis `insufficient`, so validation rejected it. This directly demonstrates that the confidence score is not a reliable probability of a supported match.
- **Avanza:** four distinct group-company IDs occur on the contact page. The model abstained because it could not establish whether the bank or holding company was the website operator. Retain this ambiguity instead of forcing the ESEF reporting-company reference ID to be the answer.
- **NCC:** no supported identity facts were extracted. The model claimed an organisation number was present but invalid because it lacked a VAT prefix/suffix. Inspection of both the actual model inputs and all four original saved HTML pages found no NCC organisation number. That explanation is unsupported; this case is not evidence that direct ID extraction alone would recover the match. Three model inputs were truncated, and substantial cookie text consumes the page budget.
- **Elon:** `elongroup.se` failed with `ERR_HTTP_RESPONSE_CODE_FAILURE` before classification.
- **Arise:** the model returned no facts even though all four model-input pages explicitly contain `Head office Arise AB Linjegatan 7 302 50 Halmstad Sweden`. This is an identity-extraction miss, independent of database retrieval.
- **Byggmax:** the model classified the site as `online_store`; the lookup stopped after one page and one classification call with zero registry searches. This is the intended category exclusion, not a missed company match.
- **Mangold — supported operator match, different from reference:** the filing reference is Mangold AB (`5566285408`), but the actual contact page states `Mangold Fondkommission AB … Org. nr: 556585-1267`, and the homepage copyright names the same company. The returned `5565851267` is therefore supported as the website operator; do not score it as a wrong-company result merely because it differs from the reporting company. The extraction also incorrectly included the website designer `Decision by Heart` from `Producerad av Decision by Heart` as a trading name, despite instructions excluding designers. The exact organisation-number match prevented that unrelated name from determining the result.
- **Genova:** the identity response included placeholder registration numbers (`not found`, `none`) and one empty `source_url`. Pydantic rejected the entire response, so supported facts from other entries were never considered. This is an output-contract/repair issue, not a database failure.
- **Brinova:** the model selected the reference ID at confidence 0.97 but used `basis=insufficient`, despite affirmative reasons. An inactive same-normalized-name registry company was also returned. The model's reasoning and decision fields disagree; this needs explicit ambiguity handling rather than accepting the high score.
- **Hufvudstaden (additional cohort):** the model invented HTML-style quotes and an organisation number `556639-0183` instead of the reference `5560128240`. All unsupported facts were rejected, so no incorrect company was returned. Preserve this evidence-check protection while improving extraction.
- **Latour (additional cohort):** website `Investment AB Latour (publ)` normalizes to `investmentlatour`, while registry `INVESTMENTAKTIEBOLAGET LATOUR` normalizes to `investmentaktiebolagetlatour`. A separate read-only diagnostic confirmed the correct row passes the retrieval filter but scores 0.5714, below the last top-ten candidate at 0.6875. Consequently the right company never reaches the assessment model. The model then proposed unrelated Investment AB Urbanor (`5563372571`) at confidence 0.98 while its own explanation says it should return null; deterministic validation rejected this wrong proposal. Improve legal-form normalization and distinctive-name-token retrieval before asking any model to rank candidates.
- **Indutrade (additional cohort):** both the verified organisation number and candidate ID are `5560179367`, with a supported `Indutrade AB` legal-name quote. The model selected that ID at confidence 0.99 but marked `basis=insufficient`; the validator checks that label before exact-ID evidence and rejected the proposal. This is another actionable false-negative path.

## Follow-up design from this review

Prioritize direct extraction of labelled Swedish organisation/VAT numbers from contact and legal-page evidence, followed by exact registry searches. The current implementation already searches extracted IDs before names, but finding the IDs still depends on the general model. The saved Addtech and Axfood page text contains their correct numbers even though identity extraction timed out; Stendörren's page contains the correct number which the model altered. Keep source quotes and distinguish observed IDs from verified operator IDs, since customers, subsidiaries and processors may also be mentioned.

An optional Jev candidate decision can assess multiple returned registry companies, report per-candidate confidence and evidence, and explicitly choose no reliable match. Scores should be labelled model confidence, not calibrated probability. Deterministic evidence checks must remain separate from this ranking; high confidence cannot override conflicting identifiers. This benchmark keeps Jev disabled to preserve a comparable local-model baseline.

## Evaluation limits

The initial cohort is frozen before execution: Addtech plus 20 distinct active Swedish companies with suggested-primary `.se` domains explicitly referenced in 2024 ESEF filings, selected by stable domain hash. IDs and company names are withheld from the lookup request. An additional cohort uses the next distinct DNS-resolving companies under the same selection rule to compensate for unreachable initial domains; initial failures remain counted.

ESEF domain associations identify a reporting company, which may differ from a website's legal operator or subsidiary. Any different-company result requires operator-evidence review. Retail-site exclusion may be correct even when the domain belongs to a registered company. This is a small listed-company sample, not an estimate for all Swedish domains.

Each attempt retains status, result JSON and a full debug trace with model requests/responses, elapsed times and parameterized read-only ClickHouse searches. No company-domain association is written. The benchmark uses four pages, two concurrent crawls, the saved model defaults, and no retries that replace original outcomes. Failed model calls may not report token usage; totals only include usage actually returned by the endpoint. No monetary cost is reported by the local endpoint.
